# Projeto: Guia da TI

Quero desenvolver o **Guia da TI**, disponível em `guiadati.com`.

O Guia da TI será uma plataforma open source e colaborativa para descobrir recursos relacionados ao ecossistema de tecnologia.

A ideia é funcionar como um grande diretório/guia da área de tecnologia, mantido parcialmente pela própria comunidade através de Pull Requests no GitHub.

Não quero limitar o projeto apenas a desenvolvimento de software.

O Guia da TI deve contemplar tecnologia de forma ampla: desenvolvimento, dados, infraestrutura, segurança, design, produto, hardware, redes, IA, carreira, educação, comunidades e outras áreas relacionadas.

---

# 1. Arquitetura geral

Quero separar o projeto em **dois repositórios**.

## Repositório 1 — aplicação

Exemplo:

`guia-da-ti/web`

Este será o projeto executado na VPS e responsável pelo site `guiadati.com`.

Ele contém:

* frontend;
* backend, se necessário;
* mecanismo de busca;
* filtros;
* mapa;
* páginas;
* SEO;
* geração das páginas;
* integração com os dados públicos.

Esse repositório não precisa ser o local onde a comunidade cadastra conteúdo.

---

## Repositório 2 — dados públicos

Exemplo:

`guia-da-ti/database`

Esse será completamente open source.

A comunidade poderá:

1. fazer fork;
2. adicionar ou alterar um recurso;
3. abrir Pull Request;
4. aguardar revisão;
5. após aprovação e merge, o conteúdo passa a aparecer no Guia da TI.

Quero evitar inicialmente banco de dados, painel administrativo e autenticação para cadastro.

O próprio GitHub será o CMS.

O repositório público será a **fonte da verdade dos conteúdos**.

A aplicação da VPS deverá consumir esses dados.

Pode ser através de JSON/YAML versionado no GitHub ou outra arquitetura simples que mantenha essa filosofia.

Priorize simplicidade, manutenção fácil e baixo custo operacional.

# 32. Performance

O projeto poderá eventualmente possuir milhares de registros.

Portanto:

* não baixar milhares de arquivos individualmente no browser;
* consolidar/indexar os dados durante build/deploy;
* gerar índice de busca;
* otimizar imagens;
* lazy-load do mapa;
* cachear dados;
* gerar páginas estáticas quando fizer sentido.

---

# 33. Sincronização com o repositório público

Quando um PR for aprovado no repositório de dados:

```text
Contributor
      ↓
Pull Request
      ↓
CI valida schema
      ↓
Maintainer aprova
      ↓
Merge
      ↓
Aplicação recebe atualização
      ↓
Build/deploy
      ↓
guiadati.com atualizado
```

Projete uma maneira simples para fazer isso.

Pode ser webhook, GitHub Action acionando deploy ou atualização periódica.

Priorize a opção mais simples e segura.

Nunca permitir que conteúdo enviado por colaboradores execute código na VPS.

Os dados externos devem ser tratados estritamente como dados não confiáveis e validados.

---

# 34. Segurança

Como o repositório recebe contribuições públicas:

* sanitizar conteúdo;
* validar URLs;
* não executar HTML enviado nos registros;
* não aceitar JavaScript;
* limitar tamanhos dos campos;
* validar schemas;
* proteger contra URLs maliciosas;
* evitar carregamento arbitrário de scripts;
* revisar imagens externas;
* tratar todo conteúdo contribuído como não confiável.

# 37. Princípio principal

O Guia da TI deve ser:

**aberto, comunitário, pesquisável e fácil de contribuir.**

A comunidade mantém os dados.

A aplicação organiza, relaciona e apresenta esses dados.

Evite overengineering.

Se algo puder ser resolvido com:

`GitHub + JSON + build`

não crie:

`banco + API + autenticação + painel administrativo`.

Antes de escrever código:

1. Analise esses requisitos.
2. Proponha a arquitetura técnica.
3. Defina a estrutura dos dois repositórios.
4. Defina o schema base dos recursos.
5. Defina a taxonomia.

Depois implemente o MVP incrementalmente.
